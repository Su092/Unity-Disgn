# 任务 08：正常启动路径冒烟测试

- 状态：**完成**（2026-11-12）
- 依据：`docs/technical-design.md` §8 自检体系

## 为什么要单独做这个

`-scheck`（实机自检）为了跑断言，会**关掉主菜单**、**关掉遥测**，直接进对局。
好处是断言不会在暂停态下跑；代价是——

> **真实玩家的启动路径从未被验证过。**

菜单能不能正常显示、点「开始」会不会崩、遥测是否真的开启——
这些只有人工试玩才知道。而这是玩家接触游戏的头 30 秒。

所以新增 `-smoke`：跑**正常路径**，只做最小断言，跑完退出。
它与 `-scheck` 是互补关系，不替代。

## 覆盖的路径

| # | 断言 | 为什么重要 |
|---|------|-----------|
| 1 | 正常启动显示主菜单 | 玩家第一眼看到的东西 |
| 2 | 菜单显示解锁项 | 面板动态生成是否正常 |
| 3 | 菜单期间游戏暂停 | 否则玩家在菜单里被敌人打 |
| 4 | 菜单期间 timeScale 为 0 | 暂停是否真的生效 |
| 5 | 正常模式遥测已开启 | 只有正常模式才该采集数据 |
| 6 | 点开始后不再暂停 | **最容易漏的一步** |
| 7 | 点开始后 timeScale 恢复 | 否则玩家盯着卡死画面 |
| 8 | 点开始后菜单已关 | 否则菜单盖住游戏 |
| 9 | 开局后敌人已生成 | 第一波有没有起来 |
| 10 | 开局后威胁值在涨 | 加压机制是否启动 |
| 11 | 玩家血量正常 | 初始化是否完整 |
| 12 | 武器就绪 | 手里的枪是否可用 |
| 13 | 正常模式下能开火 | 全链路：输入 → 结算 → 弹丸 |
| 14 | 开火扣弹 | 弹药系统 |
| 15 | 能打开背包 | Tab 是否响应 |
| 16 | 背包打开即暂停 | 与 #3 同理 |
| 17 | 能关闭背包 | |
| 18 | 关背包后能回到运行态 | 见下 |

## 一个「看着像 bug 其实是设计」的判定

第 18 条最初写成「关背包后 `timeScale` 必须为 1」，结果失败：`open=False ts=0`。

排查后确认**不是 bug**：2.5 秒战斗期间升级产生了排队的三选一，
关背包时立刻弹出三选一（`OnInventoryClosed` 的正确行为），游戏保持暂停。

断言改成：

```
关背包后能回到运行态 = (timeScale == 1) 或 (仍有排队三选一)
```

**教训**：断言写死了「理想状态」，但被测系统有合法的多态。
判据要覆盖全部合法分支，否则会稳定误报——这种误报比漏报更危险，因为它会训练人忽略红灯。

## 又一次踩到同一个坑

`smoke.log` 一开始写到了 `Build/Windows/` 而不是工程根 ——
因为播放器里 `Application.dataPath` 指向 `<exe目录>/S_Data`。

这个坑在 `SelfCheck` 里已经踩过并修过，`SmokeTest` 又犯了一次。
已抽出 `FindProjectRoot()` 向上找含 `Assets` 的目录。
